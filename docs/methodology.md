# 실험 방법

## 재고 정합성: 제어한 동시 실행

초기 재고 10개, 요청 수 32개, 요청당 수량 1개를 기본으로 합니다. 세션을 먼저 연결한 후 각 트랜잭션이 같은 재고를 읽도록 배리어에서 대기시킵니다. 모두 읽으면 쓰기를 시작합니다. 안전 구현에도 시험 전용 읽기·배리어를 넣어 같은 스케줄을 만들되 차감 판단은 조건부 UPDATE가 합니다. HTTP 경로의 안전 구현에는 이 읽기·배리어가 없습니다.

이 구성은 경합 창을 확실하게 만드는 **정합성 반례**입니다. 자연 트래픽에서의 발생 확률이나 성능을 나타내지 않으므로 재고 실험에 응답 시간·TPS 개선율을 붙이지 않습니다. 타임아웃과 연결 오류는 품절에 포함하지 않고 별도 오류로 처리합니다.

모든 구현은 READ COMMITTED를 사용합니다. PostgreSQL은 경합한 UPDATE에서 앞선 트랜잭션을 기다린 후 수정된 행에 WHERE 조건을 다시 평가합니다. 이 특성을 단일 행의 조건부 차감에 이용합니다. 여러 행의 복잡한 제약까지 자동으로 보장하는 설계는 아닙니다.

근거: [PostgreSQL 트랜잭션 격리](https://www.postgresql.org/docs/18/transaction-iso.html).

### 검증

- `sold_units`: checkout 주문의 수량 합계로 계산하며 API 성공 응답 수만 믿지 않습니다.
- `initial_stock = remaining_stock + sold_units`를 검사합니다.
- 안전 구현은 판매량이 초기 재고를 넘지 않고 잔여 재고가 음수가 아닌지 검사합니다.
- 취약 구현은 의도한 초과 판매가 발생했는지 검사합니다. 재현 실패를 성공으로 처리하지 않습니다.
- 주문 INSERT의 CHECK 위반을 유발해 재고 UPDATE가 함께 롤백되는지도 통합 테스트합니다.

## 조회 성능: 한 변수 비교

데이터 생성은 난수나 현재 시각에 의존하지 않습니다. 시작 시각, 고객 매핑, 주문 상태 규칙을 고정합니다. 고객 1에 절반을 배정하고 나머지를 999명에 분산하여 쏠림을 포함합니다. 기본 규모의 나머지 고객은 각자 수백 건 수준입니다. 실제 서비스의 분포를 대표한다고 주장하지 않습니다.

비교에서 바꾸는 것은 `orders_customer_recent_idx`의 존재입니다. PostgreSQL의 기본 키 인덱스는 양쪽에 있습니다. 동일 테이블과 SQL을 사용하며 순차 탐색을 강제로 켜거나 끄지 않습니다.

1. checkout 자료를 제거한 뒤 VACUUM ANALYZE를 한 번 실행합니다.
2. 각 구간에서 후보 인덱스를 제거/생성합니다. 생성 시간은 조회 측정에 포함하지 않습니다.
3. 고객 `[1, 2, 42, 999]`를 두 번 조회하여 동일한 8회 워밍업을 실행합니다.
4. 한 연결로 같은 고객 순서를 반복하며 `performance.now()`로 SQL 전송~행 수신 시간을 측정합니다.
5. 측정 종료 후 결과 행의 SHA-256을 대조합니다. 해시 계산은 시간에 포함하지 않습니다.
6. 구간별 네 고객에 대해 EXPLAIN ANALYZE를 별도로 실행합니다.
7. ABBA를 기본 2회 반복하고 전체·고객별·구간별 분포를 저장합니다.

파라미터는 바인딩하고 named prepared statement는 사용하지 않습니다. 자동 쿼리 재작성이나 LIMIT 변경이 없습니다. 최적화 전후가 실제로 같은 결과를 반환하는지 검증합니다.

복합 B-tree의 선두 열은 고객 조건, 다음 열들은 정렬 순서입니다. INCLUDE는 결과 열을 담지만 index-only scan 여부는 실행 계획과 가시성 맵 상태로 확인해야 합니다. 결과에서 `Heap Fetches`와 버퍼 접근도 함께 보세요. 근거: [복합 인덱스](https://www.postgresql.org/docs/18/indexes-multicolumn.html), [Index-only scan](https://www.postgresql.org/docs/18/indexes-index-only-scans.html).

## 측정 한계

- 같은 워밍업과 ABBA가 완전히 같은 물리적 캐시 상태를 보장하지는 않습니다. 인덱스 생성도 테이블을 읽습니다. OS 캐시를 비우지 않았으므로 콜드 캐시 시험이 아닙니다.
- CPU 스케줄링, Docker VM 설정, 다른 프로그램, 오토버큠 등의 영향이 남습니다. 보고서에 환경 정보를 남기고 같은 PC에서 실행 시각을 달리해 반복하세요.
- 단일 클라이언트 조회의 지연 시간입니다. 시스템 최대 TPS나 HTTP p95로 표현하면 안 됩니다.
- p95는 nearest-rank 방식이며 지정된 혼합 비율에 한정됩니다. 고객 1과 나머지 고객을 따로 해석하세요.
- 인덱스 공간은 측정하지만 INSERT/UPDATE 지연, WAL 증가, 생성 시간은 아직 측정하지 않습니다.
- 시험 결과의 예상 수치는 테스트의 판정 조건입니다. 실제 실행 결과는 `results/`에만 기록합니다.
- 한 번의 실행에서 개선이 관찰되어도 일반적인 성능 보장은 아닙니다. 통계적 유의성이나 신뢰구간은 계산하지 않습니다.

## 실험 간 간섭 방지

초기화·통합 테스트·벤치마크는 같은 PostgreSQL advisory lock을 배타적으로 사용합니다. API 주문·조회는 트랜잭션 단위 공유 잠금을 시도하며 실험 중에는 503을 반환합니다. 시험 내부 연결만 이 API 잠금 단계를 생략합니다. 협력하지 않는 직접 SQL 접속까지 막는 권한 체계는 아니므로 실험 중 수동 SQL은 실행하지 마세요.

## 재현할 때 남길 항목

`results.json`에 PostgreSQL·Node 버전, 실행 환경, 소스 해시, 주요 DB 설정, 데이터셋 정보, 고객 순서와 표본 수를 저장합니다. Docker에서는 추가로 `docker version`, `docker compose version`, `docker image inspect postgres:18.4-bookworm` 결과와 Docker Desktop CPU·메모리 설정을 별도 보관하면 좋습니다.
