# 변경별 설계 기록

아래 번호는 구현 단계이며 Git 커밋이 존재한다는 뜻은 아닙니다. 각 단계의 SQL과 실행 결과를 면접에서 연결해 설명하는 용도입니다.

| 단계 | 문제와 변경 | 선택 이유 | 검토한 대안 | 검증 |
|---|---|---|---|---|
| 01 | 전용 `lab` 스키마, products·orders, CHECK·FK 추가 | 실험 초기화 범위를 한정하고 수량·금액·참조 무결성 표현 | 도메인별 다수 테이블: 초기 검증 범위에 비해 복잡 | seed 행 수, 제약 위반 테스트 |
| 02 | 결정적 30만 주문·고객 쏠림 생성 | 전후 같은 데이터와 파라미터를 사용하고 핫 고객/일반 고객 비교 | 균등 난수: 분포와 재현성 통제가 더 필요 | 데이터셋 버전·행 수·ID/고객 합계·시각 기록 |
| 03 | 읽기→계산→덮어쓰기 취약 구현과 배리어 추가 | 갱신 유실을 운에 맡기지 않고 확실한 반례 생성 | sleep 삽입: 스케줄 재현성이 약함 | CHECK 통과 상태의 초과 판매와 재고 보존 실패 |
| 04 | 조건부 UPDATE RETURNING + 같은 트랜잭션의 INSERT | 단일 상품 차감 조건을 DB의 행 갱신 시점에 평가 | SELECT FOR UPDATE, 낙관적 버전 검사, SERIALIZABLE | 동시 32요청, 품절 거절, 여러 개 주문, INSERT 실패 롤백 |

| 07 | API 공유 잠금 / 실험 배타 잠금 | API 변경이 측정에 끼어드는 것을 감지·거절 | API 수동 중지: 사용자가 빠뜨릴 수 있음 | 실험 잠금 중 API 공유 잠금 503 테스트 |

## 동시성 대안의 선택 기준

**SELECT FOR UPDATE:** 읽은 뒤 여러 판단이 필요하면 명확합니다. 트랜잭션 안에서 잠금과 검증을 유지해야 하고 잠금 보유 시간이 길어질 수 있습니다. 여러 상품 주문은 일관된 상품 ID 순서로 잠그는 방식도 필요합니다.

**낙관적 버전 검사:** `WHERE version = 읽은 버전`으로 충돌을 감지할 수 있습니다. 충돌이 적을 때 유용하나 재시도 정책과 실패 응답을 설계해야 합니다.

**SERIALIZABLE:** 복잡한 트랜잭션 간 제약에 사용할 수 있지만 serialization failure에 대한 전체 트랜잭션 재시도가 필요합니다. 단일 행의 수량 조건에는 이번 조건부 UPDATE가 더 작은 구현입니다.

**Redis 분산 잠금:** 단일 PostgreSQL 행에 대한 정확성을 위해 별도 시스템과 잠금 만료 문제를 추가할 이유가 부족해 사용하지 않았습니다.

## 조회 대안의 선택 기준

`customer_id` 단독 인덱스는 필터링에 도움을 줄 수 있지만 최신 50건 정렬 비용이 남습니다. INCLUDE 없는 복합 인덱스는 더 작고 쓰기 비용이 낮을 가능성이 있으므로 다음 실험 후보입니다. 어떤 대안이 더 낫다는 수치는 아직 측정하지 않았습니다.

OFFSET→keyset 페이지네이션은 깊은 페이지에서 별도 가치가 있지만 이번에는 첫 50건 조회를 고정했습니다. 한 번에 SQL과 인덱스를 모두 바꾸면 개선 원인을 구분하기 어려워 범위에서 제외했습니다.

## 의도적으로 남긴 확장 과제

- 요청 멱등성 키와 같은 키·다른 본문 충돌 처리, 응답 유실 후 재시도 테스트.
- 상품 여러 개의 원자적 주문과 잠금 순서, 데드락 재시도.
- 주문 취소·재고 복원 시 상태 전이의 중복 방지.
- 인덱스 전후 쓰기 처리량·WAL·저장 비용 실험.
- 제한된 연결 풀, API 계정과 마이그레이션 계정 분리.
- WAL 아카이빙·PITR, 실제 복원된 주문 정합성 확인.
