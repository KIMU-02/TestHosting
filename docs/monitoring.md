# 운영 모니터링과 장애 확인

## 사용법

Update-Dashboard.cmd 실행 후 http://localhost:8080/#monitoring 에서 `상태 확인`을 누릅니다. 필요하면 `5초마다 갱신`을 켭니다. 기본은 수동이며 숨겨진 탭에서는 자동 조회하지 않습니다. 성능 실험 중에는 자동 조회를 끄고 화면 조작을 멈춥니다.

`View-Logs.cmd`를 실행하면 컨테이너 상태와 API/DB의 최근 로그 80줄을 볼 수 있습니다. 이 명령은 데이터·컨테이너를 변경하지 않습니다. API는 각 완료 요청의 정규화된 경로·상태·소요 시간·요청 ID를 JSON 한 줄로 stdout에 남깁니다. 오류 표의 요청 ID를 로그에서 찾습니다. 요청 본문·쿼리 문자열·고객 번호·멱등성 키는 이 요청 로그에 넣지 않습니다.

## 지표의 정확한 의미

- API 누적 완료 수와 연결 종료 수는 현재 프로세스 시작 이후 값이며 재시작하면 초기화됩니다.
- p95·평균·오류율·경로별 표는 최근 완료 요청 최대 1,000건의 창입니다. 시간 기준 5분 창이 아닙니다. 표본 시작 시각과 개수를 함께 확인합니다. 표본이 없으면 p95를 0으로 만들지 않습니다.
- 상태 확인·health·live·정적 자산 요청은 제외합니다. 주문·조회·보고서 API 및 알 수 없는 경로의 응답은 포함합니다. 4xx와 5xx 모두 지연 표본에 포함합니다.
- 지연은 Node가 요청을 받은 시점부터 응답 finish 이벤트까지입니다. DB 연결·쿼리·응답 생성이 포함되며, 클라이언트가 응답을 받은 시각이나 브라우저 렌더링 완료 시간은 아닙니다.
- 4xx는 품절·입력 오류·키 충돌 등이며 5xx 서버 오류율의 분자에 넣지 않습니다. 응답 전에 연결이 끊긴 요청은 별도 중단 수에 포함하고 정상 완료 표본에는 넣지 않습니다.
- DB 값은 조회 시점의 스냅샷입니다. 전체 서버 연결은 관측 연결을 포함한 client backend 수이며, 현재 DB 연결·active 수는 관측 연결을 제외합니다. max_connections에는 예약 슬롯이 있으므로 차이가 곧 사용 가능한 연결 수는 아닙니다.
- 잠금 대기는 `wait_event_type='Lock'`, 열린 채 유휴 트랜잭션은 `idle in transaction` 상태를 확인합니다. PID 목록은 최대 20개입니다. SQL 본문은 화면에 노출하지 않습니다. PostgreSQL 통계의 정의는 [공식 PostgreSQL 18 문서](https://www.postgresql.org/docs/18/monitoring-stats.html)를 참고했습니다.
- DB 통계 접근에 실패하면 확인 불가로 표시하며 이전 값이나 0을 정상 상태로 표시하지 않습니다. 모니터링 API 자체는 200과 database.status=unavailable을 반환할 수 있습니다.
- `/live`는 HTTP 프로세스 응답 여부, 기존 `/health`는 DB와 lab.dataset 접근 여부를 검사합니다. Docker readiness 검사에는 기존 `/health`를 유지합니다. 시작 시 마이그레이션에 실패하면 API는 시작하지 않습니다.

## 변경 이유·대안·검증

| 변경 | 이유 | 대안 | 검증 |
|---|---|---|---|
| 크기 제한 메모리 표본 | 별도 서비스 없이 로컬 관측 시작, 메모리 상한 유지 | Prometheus/Grafana는 장기 보존·여러 서버 집계에 적합, 후속 확장 | 창 축출·빈 표본·4xx/5xx 단위 테스트 |
| 경로 정규화와 요청 ID | 로그 연계 및 개인정보·고카디널리티 경로 방지 | 원본 URL 기록은 고객/주문 식별자를 포함할 수 있음 | 로그에 쿼리 문자열 미포함 및 HTTP ID 대조 |
| finish/close 구분 | 연결 중단을 성공으로 오인하지 않음 | finish만 감시하면 중단 누락 | 중복 집계 방지·중단 수 테스트 |
| pg_stat_activity와 blocking PID | DB 세션의 대기 원인을 실제 상태로 확인 | 연결 수만으로 잠금 원인을 알 수 없음 | 별도 DB advisory lock으로 대기 생성·해제 검사 |
| 선택적 5초 갱신 | 불필요한 관측 부하를 줄임 | 무조건 polling은 실험에 영향을 줄 수 있음 | 브라우저 수동 조회, polling 경로 집계 제외 테스트 |
| 관측용 DB 쿼리 2초 제한 | 통계 조회가 장시간 실행되는 것을 제한 | 무제한 쿼리는 장애 시 관측 자체가 누적될 수 있음 | DB 실패 반환 단위 테스트; 실제 DB 중단 시험은 미실행 |

## 확인 순서

1. 화면 자체가 안 열리면 Docker Desktop과 API 컨테이너 상태를 확인합니다. View-Logs.cmd의 compose ps에서 health를 봅니다.
2. DB 확인 불가면 db 컨테이너 로그·접속 설정·통계 조회 권한을 확인합니다.
3. 잠금 대기가 있으면 대기 PID와 차단 PID를 기록하고 열린 트랜잭션이 정상적으로 COMMIT/ROLLBACK되는지 확인합니다. 단순 대기와 deadlock은 다릅니다.
4. 5xx가 있으면 해당 요청 ID의 API 로그를 확인합니다. 503은 성능 실험의 배타 잠금으로 주문을 의도적으로 막은 경우도 있습니다.
5. p95가 커지면 표본 수·경로별 분포·DB 대기를 함께 확인합니다. 표본 구성이 바뀐 운영 p95를 과거 단일 연결 SQL 벤치마크와 직접 비교하지 않습니다.

## 검증 기록과 한계

2026-09-12 별도 Windows PostgreSQL 18.4(port 55439), 로컬 Node API(port 8084)에서 단위 테스트 13개, 실제 잠금 대기/해제 검사 1개, HTTP 자산·상태·오류 ID·960개 기존 CSV 표본 검사가 통과했습니다. 브라우저에서 상태 확인 후 DB 통계 표시를 확인했습니다. Docker 새 이미지 반영은 Update-Dashboard.cmd 실행 후 로그로 확인합니다. 기존 실험 파일·사용자 Docker 주문·재고는 변경하지 않았습니다.

장기 지표 저장, 외부 알림, SLO, 분산 추적, CPU/디스크/호스트 메트릭은 아직 없습니다. stdout 로그의 보존은 Docker 설정에 따릅니다. 운영 메트릭 수집과 로깅 자체도 비용이 있으며 그 오버헤드는 이번에 측정하지 않았습니다. 상태가 '조회 완료'인 것은 모든 서비스가 정상이라는 보증이 아닙니다.
