## 실행

Docker Desktop에서 기존 프로젝트가 실행 중인 상태로 `Backup-Restore.cmd`를 실행합니다. API 재빌드는 필요하지 않습니다. 별도 Node.js나 PostgreSQL 클라이언트 설치도 필요하지 않습니다. Windows PowerShell이 db 컨테이너에 포함된 PostgreSQL 도구를 호출합니다.

실행마다 `results/recovery/<UTC시각_임의값>/`에 다음을 남깁니다.

- `portfolio.dump`: custom format 논리 백업. 바이너리 파일을 PowerShell 파이프로 전달하지 않고 파일로 생성·복사합니다.
- `report.json`: 도구/서버 버전, 파일 크기와 SHA-256, 단계별 성공 여부, 실제 백업·복원·검증 소요 시간, 복원 DB 집계, 정리 상태.
- `commands.log`: 외부 명령의 진단 출력. 실패 시 확인합니다.

성공 조건은 report.json의 **status=verified, cleanup=removed**입니다. 백업만 생긴 상태는 성공이 아닙니다. 실패 기록도 삭제하지 않습니다. 백업과 보고서는 Git에 자동으로 포함하지 않으며, 보관 파일은 실행마다 늘어납니다.

## 설계 이유와 대안

| 변경 | 설계 이유 | 대안 | 검증 |
|---|---|---|---|
| pg_dump custom format | 일관된 논리 스냅샷과 pg_restore 사용 | 파일 디렉터리 단순 복사는 실행 중 DB의 정합성을 보장하지 않음 | 실제 pg_restore 완료와 복원 SQL 검사 |
| 고유 이름의 별도 DB에 복원 | 원본 portfolio 덮어쓰기 방지 | 원본에 --clean 복원은 기존 객체를 제거할 수 있음 | 생성 대상 정규식, SQL 내부 DB 이름 검사 |
| template0에서 생성, 단일 트랜잭션 복원 | 깨끗한 대상에 복원하고 중간 오류를 실패로 처리 | 오류를 무시하면 일부 객체 누락 가능 | pg_restore --exit-on-error --single-transaction 및 명령 종료 코드 검사 |
| 백업 파일 SHA-256 기록·재확인 | 검증에 사용한 파일을 식별하고 복원 전 변경 감지 | 파일 크기만으로 동일 파일 여부 판단 불가 | Get-FileHash 결과 기록 및 재비교 |
| 행 수·제약·요청 키 연결 검사 | 파일 생성 성공과 읽을 수 있는 복원을 구분 | pg_dump 종료 코드만 확인하면 복원 문제를 발견하지 못함 | 과거 주문 수=dataset, FK/제약 복원, 요청 키와 주문 내용 일치 |
| 복원 DB에서 주문 쓰기 후 롤백 | identity 시퀀스와 쓰기 가능 여부 확인 | SELECT만 확인하면 다음 INSERT의 시퀀스 충돌을 놓침 | 새 ID가 max(id) 초과, 재고 변경/복원 확인, 트랜잭션 롤백 |
| 생성 성공한 임시 DB만 정리 | 원본/기존 DB 삭제 방지 | 이름을 사용자가 입력받으면 오입력 위험 | 생성 플래그·이름 정규식 모두 확인, 정리 실패를 성공으로 기록하지 않음 |

pg_dump는 동시 쓰기 중에도 내부적으로 일관된 스냅샷을 생성합니다. 따라서 백업 후 원본의 현재 행 수와 복원 DB 행 수가 달라질 수 있어, 두 시점의 수치를 무조건 비교하지 않습니다. 이 검증은 원본과 복원본 전체 행의 비트 단위 동일성을 증명하지 않습니다. [PostgreSQL 18 pg_dump 공식 문서](https://www.postgresql.org/docs/18/app-pgdump.html)

백업 동안 원본에 데이터를 쓰는 명령은 실행하지 않습니다. 읽기 I/O와 스키마 잠금은 발생하므로 성능 실험과 동시에 실행하지 마세요. 스키마 잠금 대기가 10초를 넘으면 백업은 실패 처리합니다.

## 실제 검증 범위 — 2026-09-12

- Windows PowerShell 구문 검사 통과.
- 별도 Windows PostgreSQL 18.4(port 55439)에서 `npm run test:recovery-sql` 통과: 원본 DB 쓰기 거부, 임시 DB 정상 데이터 검사와 롤백, 잘못된 요청 키 연결 거부. 테스트용 DB는 제거했습니다.
- 이 테스트는 작은 검증용 테이블을 직접 만들어 SQL을 시험한 것입니다. pg_dump/pg_restore의 전체 실행 성공을 의미하지 않습니다.
- 전체 네이티브 실행은 검증 도구 묶음에 pg_dump.exe가 없어 실패했으며 해당 report.json을 보존했습니다. SQL 검사의 첫 실행은 임시 PostgreSQL이 꺼져 있어 실패했고, 검증 서버를 시작한 뒤 재실행하여 통과했습니다.
- 에이전트 환경은 Docker CLI 실행이 접근 거부되어 Docker 전체 백업·복원은 아직 미검증입니다. 사용자가 Backup-Restore.cmd를 실행하면 실제 결과가 보고서에 기록됩니다. 성공 시간·복원 행 수는 미리 작성하지 않았습니다.

## 결과 해석과 복구 범위

복원 완료 시간은 pg_restore 명령만의 경과 시간입니다. 장애 탐지·서버 준비·접속 전환을 포함한 서비스 RTO가 아닙니다. RPO는 마지막 성공 백업 이후 데이터 손실 가능 구간이며, 이 도구는 자동 주기 백업이나 WAL 기반 시점 복구(PITR)를 제공하지 않습니다.

현재는 단일 DB의 데이터·스키마 복원 연습입니다. --no-owner/--no-acl을 사용하므로 사용자 역할·권한·비밀번호·서버 설정·다른 DB까지 복구하지 않습니다. 동일 PC의 백업은 PC/디스크 전체 장애를 대비하지 못합니다. 별도 저장소 복제와 실제 장애 전환은 후속 단계입니다.

SQL 쓰기 시험은 트랜잭션을 롤백하지만 시퀀스의 nextval 증가는 롤백되지 않습니다. 그래서 시험 대상 DB는 검증 후 삭제하고, 보관한 dump 파일은 수정하지 않습니다.

## 실패했을 때

1. Docker Desktop과 db 컨테이너 실행 상태를 View-Logs.cmd에서 확인합니다.
2. 실패 보고서의 error와 commands.log를 확인합니다. 실패한 덤프 파일을 정상 백업이라고 판단하지 않습니다.
3. cleanup=failed이면 report.json에 적힌 임시 DB 이름을 확인합니다. 자동 도구는 원본 DB 강제 삭제나 연결 강제 종료를 하지 않습니다.
4. 파일 공간 부족·DB 역할 권한·스키마 잠금 여부를 해결하고 새 실행으로 다시 검증합니다. 기존 실패 기록은 비교 자료로 남깁니다.
