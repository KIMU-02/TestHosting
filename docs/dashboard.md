# 대시보드 추가 기록

## 성능 보고서 확장 — 2026-09-12

단일 p95 막대에서 고객별·지표별 비교, 반복 구간, 실행 계획, 정합성 시험과 재현 조건을 함께 읽는 보고서로 확장했습니다. 기존 Docker 실행 기록을 사용하며 새로운 성능 측정을 했다는 의미는 아닙니다.

| 변경 | 설계 이유 | 대안 | 검증 방법 |
|---|---|---|---|
| 고객 필터와 평균·p50·p95 선택 | 혼합 표본이 가리는 고객별 차이를 확인 | 전체 평균만 표시하면 데이터 편향을 설명하기 어려움 | 고객 42·평균 선택과 원본 집계 비교 |
| 8개 구간 차트·고객별 표 | 반복 간 변동과 ABBA 순서를 공개 | 한 번의 측정만 선택하면 순서 효과를 숨김 | 저장된 구간별 집계를 그대로 표시 |
| 실행 계획·버퍼·Heap Fetches | 개선 원인을 수치와 접근 경로로 설명 | 실행 시간만 제시하면 원인 설명 부족 | 루트 버퍼만 사용해 자식 노드와 중복 합산하지 않는 단위 테스트 |
| 재고 시험 전체 회차 | 음수 재고 여부 외에 승인량·보존식을 확인 | 잔여 재고만 확인하면 lost update를 놓침 | 승인·품절·초과 판매·잔여 재고·오류·보존식 표시 |
| CSV·JSON 다운로드 | 면접관이 표본과 집계를 검토할 수 있도록 제공 | 브라우저 Blob 대신 HTTP attachment로 제공 | CSV 960개 행 전부 API 표본과 대조, 잘못된 run은 404 |
| 환경·한계 공개 | 결과의 적용 범위를 명확히 설명 | 수치만 강조하면 운영 성능으로 오해 가능 | 소스 해시·DB 버전·워밍업·연결 수 표시 |

검증: 단위 테스트 9개 통과, 별도 Windows PostgreSQL 검증 DB의 localhost:8082에서 HTTP 검사 통과. 브라우저에서 기본 p95 및 고객 42 평균 전환을 확인했습니다. 390px 뷰포트에서 문서 전체 가로 넘침이 없었습니다. 다운로드 응답 내용과 attachment 헤더는 HTTP 검사로 검증했으며, 인앱 브라우저의 실제 파일 저장 완료는 확인하지 못했습니다. Docker 새 이미지 적용은 Update-Dashboard.cmd 실행 후 로그로 확인해야 합니다.

## 구현

기존 Node HTTP 서버의 `/`를 관리 화면으로 변경했습니다. 기존 `GET /orders`, `POST /orders`, `/health`는 유지했습니다. 서버에 React 등의 의존성을 추가하지 않고 정적 HTML·CSS·JavaScript를 같은 주소에서 제공합니다.

| 변경 | 이유 | 대안 | 검증 |
|---|---|---|---|
| 한 화면의 주문 폼·재고 카드·주문 목록 | Docker·JSON에 익숙하지 않아도 브라우저로 조작 | 별도 프런트엔드 서버: 이번 범위에서 빌드·실행 부담 증가 | 브라우저 주문 생성→재고 차감→목록 갱신 |
| `/api/overview` | 등록 상품과 직접 생성 주문의 현황 제공 | history 주문을 모두 합산: 현재 재고와 의미가 맞지 않음 | 실제 DB 집계·READ ONLY 스냅샷 확인 |
| `/api/orders` | 기존 벤치마크 SQL을 바꾸지 않고 수량·원본 구분을 추가 | 기존 SQL 변경: 이전 성능 실험의 질문까지 변경 | 고객 필터·빈 목록·입력 검증 |
| `/api/measurements` | 완료된 Docker 결과만 읽어서 표시 | 숫자 하드코딩: 새로운 결과·실패 상태를 반영 못함 | 최신 완료 기록 선택·미완성 JSON·빈 상태 테스트 |
| API에 results 읽기 전용 볼륨 | 화면에서 기록을 읽되 실험 결과를 수정하지 않음 | 결과를 이미지에 복사: 새 결과가 화면에 반영되지 않음 | Compose YAML 설정 확인, 재빌드 후 HTTP 검사 제공 |
| 수동 새로고침·제출 중 버튼 비활성화 | 명시적 상태 갱신과 중복 클릭 억제 | 자동 POST 재시도: 응답 유실 시 중복 주문 위험 | 품절·성공 메시지·재고 갱신 |

최초 대시보드는 버튼 비활성화만 제공했습니다. 이후 서버 멱등성 및 취소·재고 복원을 추가했으며, 현재 동작·설계·검증은 [checkout.md](checkout.md)에 기록했습니다. 모니터링은 후속 단계입니다.

## 데이터 의미

- 현황 카드의 주문 수·판매 수량은 모든 고객의 `checkout`·`paid` 주문입니다.
- 과거 주문은 `history`로 분리하고 목록에 실험 데이터라고 표시합니다.
- 화면의 금액은 cents를 USD로 표현하며 원화로 임의 변환하지 않습니다.
- 목록 시각은 `Asia/Seoul`로 표시합니다.
- 그래프는 저장된 측정 시각·소스 해시·표본 수를 함께 표시합니다. 새 대시보드 코드에서 다시 측정했다는 주장은 하지 않습니다.
- 대시보드 추가 전의 측정 코드가 들어 있는 ZIP을 출력 폴더의 `postgres-order-lab-benchmark-v1.zip`으로 별도 보존했습니다. 기존 원본 결과·감사 기록은 당시 버전의 증거입니다.

## 검증 상태

2026-09-11 별도 Windows PostgreSQL 18.4 검증 DB와 `localhost:8081`에서 확인했습니다. 기존 Docker DB의 주문·재고는 변경하지 않았습니다.

- 단위 테스트 8개 통과: 기존 6개 + 측정 기록 선택·빈 상태 2개.
- 실제 브라우저에서 고객 700001의 수량 2개 주문 생성: 재고 10→8, 주문 수 0→1, 판매 수량 0→2, 새 주문 목록 표시.
- 999개 요청에 품절 안내가 표시되고 추가 주문이 생성되지 않음.
- 주문이 없는 고객의 빈 목록 안내 확인.
- 저장된 Docker 실측 p95 49.075ms / 0.838ms 표시 확인.
- 데스크톱과 390px 모바일 화면 시각 검사, 모바일에서 페이지 전체 가로 넘침 없음. 긴 주문 표는 내부 가로 스크롤 사용.
- HTTP 정적 자산·상품 현황·고객 목록·잘못된 고객 값·측정 기록 검사는 `node test/dashboard-http.mjs`로 재현할 수 있습니다.

현재 에이전트 환경은 Docker CLI 실행이 거부되어 새 이미지의 Docker 적용은 사용자 실행이 필요합니다. `Update-Dashboard.cmd`는 이미지 빌드→단위 테스트→API 기동→읽기 HTTP 검사를 수행하고 `results/dashboard-update.log`에 기록합니다. 데이터 초기화는 하지 않습니다.
